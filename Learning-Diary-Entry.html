4a. Implementation overview
    In which function(s) do alpha-beta cutoffs get detected in your
    code?  Briefly describe the data flow: how does a cutoff in a
    deep recursive call propagate back to stop exploration of siblings?

Cutoffs are detected inside the minimax method, right after each child’s value is backed up. At a max node (X to move), the search stops when best_val >= beta. At a min node (O), it stops when best_val <= alpha. Otherwise, the node narrows its own window, alpha = max(alpha, best_value) at a max node or beta = min(beta, best_value) at a min node. On a cutoff, the loop over children breaks. Our generator builds children very lazy, so the remaining siblings are never even created. Alpha and Beta are passed down as arguments to each recursive call, so every node searches inside the window inherited from its ancestors. When a deep node cuts off, it returns early with a value outside its parent window. The parent then compares them with the bound, and may cut it off in turn.

4b. Effectiveness measurement

    state) with alpha-beta ON vs. OFF, at the same search depth
    (depth 3 or more).  Report the number of static evaluations in

    is the percentage reduction?

We compared our agent with alpha-beta pruning enabled and disabled on autograder.MM_TEST_STATE, with O to move. Zobrist hashing was disabled and no time limit was applied. In our code, minimax calls evaluate at the leaves. evaluate increments num_static_evals_this_turn, which we used to measure the number of evaluation calls. When alpha-beta pruning was false, the search had 21 evaluations. When it was true, it had 12 evaluations and had six cutoff events. So, when alpha beta is on, we save on 9 evaluations (21-12). Therefore, the percentage reduction relative to the plain minimax is (21-12) / 21 * 100 = 42.86%. Our pruning checks are located inside the minimax, where an X/MAX node stops examining the children when best_val <= alpha. These checks reduce the number of leaves reaching evaluate. Both still returned the same result of (1, 2) and a backed up value of 0, which shows that pruning still leads to the same result. An additional note is that the unpruned count is 21 instead of 24 because we established an extra check that would stop when a state reaches a winning position rather than reaching the entire depth limit.

4c. Conceptual question — correctness of pruning
    Explain in your own words why alpha-beta pruning is *correct*:
    that is, why can we safely prune a subtree without risking that
    we miss the optimal move?  Your answer should be specific enough
    that it could not have been written without understanding the
    algorithm — for example, identify what invariant about alpha and
    beta values makes the cutoff safe.

Alpha is the value the maximizer is already guaranteed by some alternative higher up on the current path. Beta is the same guarantee for the minimizer. Together they hold an invariant: any node whose value falls outside the window alpha beta cannot be reached by optimal play, because one of the two players already has a better option elsewhere and would never choose the path leading to it.

Section 5 — Static Evaluation Analysis (10 pts: ~4 feature design, ~4 concrete example, ~2 limitations) 
5a. Feature design
    What features does your static_eval function use to score a board?
    (Examples: counts of X's and O's in rows/columns/diagonals,
    weighted partial lines, winning-threat detection, forbidden-square
    awareness.)  Explain the intuition behind the scoring formula.

Our static_eval examines every length-k segment horizontally, vertically, and diagonally and ignores segments containing forbidden squares or both players’ tokens.

For each eligible segment, our code counts its X and O tokens using segment.count('X') and segment.count('O'). If it only contains Xs and blanks, we add 10**(x_count - 1) to the score. If it contains Os and blanks, we subtract 10**(o_count - 1). One token contributes +-1, two contributes +-10, and three contributes +-100, which prioritizes lines that are about to be completed since it represents a winning opportunity. This encourages the search to value threats or wins over lines that don’t have a potential winning opportunity. We also want to subtract O’s opportunities because the agent needs to prevent the opponent from winning as well.

If x_count == k, the function returns win_score, and if o_count == k, it returns -win_score. We calculate the win_score as 4 * rows * columns * 10**k + 1 so a win is guaranteed to outweigh the partial line scores. After checking all the segments, the function returns 0 if the count_blanks(state) == 0`, otherwise it will return the accumulated score.

5c. Limitations
    Describe at least one type of board position where your static_eval
    is likely to give a misleading score, and explain why.

Using the board above, this board position is also an example of when static_eval is likely to give a misleading score. Our evaluator returns a deceivingly high number for the row . X X X X since it sees that the X’s pieces align four in a row which brings it closer to a win. The issue is that O moves next and easily occupies the square which blocks the win. The contribution of that row would then be O X X X X which drops the score to 0. This kind of evaluation shows that the formula only counts unblocked lanes without considering who’s next.

Our compose_utterance method picks a dialogue category according to the current situation and state of the board. One difficulty that occurred was the dialog feedback loop. In the self-play, both agents both said "Losing? Finally, something we agree on" for about 40 moves stright. The reply lines that contained the keyword “losing” would trigger a constant cycle and would influence the other agent to say the phrase again as well. We fixed it by setting reply lines to no longer contain trigger words or “?”, and the same reply can’t be used twice in a row.

Another challenge was making the computation explanations accurate. When testing the agent, it described the search as “minimax with alpha-beta and iterative deepening” even when pruning was disabled or the AUTOGRADER mode only performed one fixed depth search. The cause was that the text was hardcoded, so to fix this we recorded the actual search and selecting the keywords from those settings (including the depth, evaluation calls, cutoff events, elapsed time) and displaying that.

We also encountered a bug where after the timed search ended for minimax, a later call to the function would immediately raise SearchTimeout. The previous deadline was still stored on the agent, so calling minimax again would inherit the expired time limit which is why it would raise the error. We added a finally block so it would clear the deadline state when a search is completed, timed out, or hit an exception.
